# Duplicate taker-chosen swap id overwrites live swap state in handle_swap_details

- **Finding ID:** 3
- **Severity:** Medium
- **State:** pending
- **Scanner:** llm-code-review
- **Location:** src/maker/handlers.rs:477-504
- **Job:** 3
- **CWE:** CWE-20
- **Fingerprint:** c1e29cfb0c7862cc9823c35f8a2a7ee41c9b4970679deaf9b3e8ce95e58a5d21

## Description

`handle_swap_details` never checks whether the taker-chosen `SwapDetails.id` is already in use before calling `maker.store_connection_state(&details.id, state)` (line 504). Swap ids are generated by the taker (documented as a "Unique 8-byte ID" in `SwapDetails`), so a malicious taker trivially knows and can reuse an id — including the id of their own in-flight swap — from a fresh connection (the per-connection state only requires the TakerHello -> GetOffer -> SwapDetails sequence, so `expect_phase` passes).

Impact, verified against `MakerServer::store_connection_state` in src/maker/api.rs (lines 1088-1176): the existing entry is taken via `swaps.entry(swap_id).or_default()` and every field is overwritten with the fresh connection state — phase resets to `AwaitingContractData`, `incoming_swapcoins`/`outgoing_swapcoins` are replaced with empty vectors, `funding_broadcast` is reset to false, and `reserve_utxo` is cleared. Consequences: (1) the idle-swap recovery watchdog `drain_idle_swaps` (api.rs:736-762) only selects swaps with non-empty `outgoing_swapcoins`, so after the clobber the maker's committed, already-broadcast funding is never picked up for timeout recovery (server.rs:466-509 spawns `recover_from_swap` from this data); (2) the liquidity-reservation check is skipped whenever the id already exists (`should_check_liquidity = !swaps.contains_key(swap_id)`), so reusing an id also bypasses the maker's over-commit protection.

Reproduction: seed stored state for id X with phase `AwaitingPrivateKeyHandover` and `funding_broadcast = true` (i.e. maker already funded the swap), then drive `handle_message` with a `SwapDetails` reusing id X from a fresh connection state. On HEAD the message is accepted (AckSwapDetails) and the stored state is reset; the test asserts rejection and fails. The regression test uses a mock `Maker` implementing the pub trait in this file; the mock must live in-crate because the trait signature mentions `pub(crate)` swapcoin types.

Note: outgoing swapcoins are also persisted in the wallet via `save_outgoing_swapcoin`, so a wallet-level manual recovery path may still exist; the defect reported here is the silent corruption of the in-memory swap state and the resulting defeat of the designed idle-swap recovery and liquidity accounting. No prior findings matched (searched: 'duplicate swap id connection state overwrite clobber', 'SwapDetails handle_swap_details liquidity recovery outgoing').
